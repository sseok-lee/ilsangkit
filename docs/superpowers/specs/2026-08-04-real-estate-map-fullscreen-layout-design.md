# 부동산 지도 허브 — 전체화면 레이아웃 전환 설계

**작성일**: 2026-08-04
**대상**: `/real-estate` (부동산 허브)
**선행 문서**: [2026-07-31-real-estate-map-explorer-design.md](./2026-07-31-real-estate-map-explorer-design.md)
**브랜치**: `feat/real-estate-map-explorer` (PR #712 위에 이어서)

---

## 1. 배경

지도 탐색기(PR #712)를 라이브에 준하는 환경에서 써 보니 두 가지가 걸렸다.

**하단 콘텐츠가 지도를 덮는다.** 스크롤하면 유형 카드·설명문·출처 블록이 뷰포트를 채워 지도가 사라진다. 자동 스크롤이나 스냅백 같은 버그는 아니고(측정: 9초간 `scrollY` 0 유지, 지도 조작 후에도 500→500 고정), 설계대로 동작한 결과다. 지도를 주역으로 만들어 놓고 그 아래 예전 허브 페이지를 그대로 붙여 둔 구성 자체가 문제였다.

**지도와 헤더의 좌우 경계가 어긋난다.** 헤더는 `max-w-[1200px]`(`AppHeader.vue:11`)인데 지도 탐색기는 full-bleed라 두 블록의 가장자리가 맞지 않는다.

## 2. 목표

- `/real-estate` 를 **지도만 있는 한 화면**으로 만든다. 페이지 스크롤 0.
- 지도와 헤더의 좌우 경계를 일치시킨다. **단 지도 폭은 줄이지 않는다.**
- 내부 링크와 푸터 고지를 하나도 잃지 않는다. **존재만이 아니라 도달 가능해야 한다.**

## 3. 비목표

- 지도 동작(줌·패닝·필터·오버레이) 변경. 이번 작업이 다루는 것은 레이아웃, 크롤 경로, 그리고 그 둘이 강제하는 목록 페이지네이션(§7.5)뿐이다.
- 백엔드 변경. `/api/real-estate/hub-summary` 라우트는 프론트 호출이 없어져도 **남긴다** — 지금 지울 이유가 없다.
- `/real-estate/{type}` 등 하위 페이지 레이아웃.

## 4. 선행 문서와의 관계

이 문서는 선행 설계의 **6.4 "하단 콘텐츠는 한 번만 렌더한다"를 폐기한다.** 6.4는 하단 콘텐츠를 데스크톱 본문과 모바일 바텀시트에 중복 렌더하지 않기 위한 규칙이었는데, 하단 콘텐츠 자체가 사라지므로 전제가 없어진다.

선행 설계의 나머지(5.4 인덱스+FORCE INDEX, 5.5 sargable, 5.6 해시, 6.1 유형 카드 7개)는 다음 항목만 바뀐다.

- **6.1 (유형 카드 7개 유지)** → 카드를 제거하고, 그 크롤 경로를 지도 필터바 링크 6개로 옮긴다(§6).

**이 페이지는 6종 전용이 된다.** 토지는 별도 모델(면적·지목 단위)이라 지도 탐색기가 다루지 않고, 필터바에도 원래 없다. 카드가 사라지면 토지는 이 페이지와 아무 관계가 없어지므로 구조화 데이터에서도 뺀다(§8). 토지 접근 경로는 GNB 드롭다운(`types/facility.ts:553`)이 계속 담당한다 — **여기서 빼면 안 된다.** 하단 카드 제거 후 `/real-estate/land` 로 가는 내부 링크는 그것 하나만 남으며, 그마저 없애면 토지 허브와 그 하위 시/도·구군·동 페이지 전체가 내부 링크 0이 된다.

## 5. 레이아웃

### 5.1 지도 전용 레이아웃 (신규 `layouts/map.vue`)

`layouts/default.vue` 는 `TrustLine`(:18)과 `AppFooter`(:20)를 본문 뒤에 렌더한다. 이 둘이 남아 있는 한 페이지 스크롤을 0으로 만들 수 없다(데스크톱 실측 합계 약 410px). 지도 전용 레이아웃을 따로 만들어 헤더와 `main` 만 남긴다.

```
layouts/map.vue
└ div.h-screen.overflow-hidden.flex.flex-col
  ├ AppHeader (wide)
  └ main#main[tabindex=-1].flex-1.min-h-0
    └ <slot />
```

- 루트가 `h-screen overflow-hidden` 이라 페이지 스크롤이 **구조적으로** 0이다. 높이 계산이 어긋나도 스크롤바가 생기지 않는다.
- `main` 에 `min-h-0` 이 필요하다. flex 자식의 기본 `min-height:auto` 는 콘텐츠보다 작아지길 거부해서, 이게 없으면 내부 오버플로가 부모를 밀어낸다.
- 스킵 링크(`#main`)는 default 레이아웃과 동일하게 유지한다. 접근성 회귀를 만들지 않는다.
- `TrustLine`·`AppFooter` 는 렌더하지 않는다. 두 역할 모두 사이드바 하단 푸터가 대신한다(§7).

`pages/real-estate/index.vue` 에 `definePageMeta({ layout: 'map' })` 를 추가한다.

### 5.2 헤더 full-width (`AppHeader` 에 `wide` prop 추가)

지도 폭을 유지하면서 경계를 맞추기 위해, 지도를 헤더에 맞추는 대신 **이 페이지에서만 헤더를 지도에 맞춘다.**

```vue
<!-- AppHeader.vue:11 -->
<div :class="['mx-auto flex h-full w-full items-center', props.wide ? '' : 'max-w-[1200px]']">
```

- `wide?: boolean`, 기본값 `false`. 기존 호출부는 전부 무변경이다.
- `transparent` prop 이 이미 같은 방식으로 들어가 있어(`AppHeader.vue:8`) 패턴이 동일하다.
- 헤더 바깥쪽 `px-4 md:px-6` 는 그대로 둔다. 사이드바·지도도 같은 가로 여백을 쓰지 않으므로 경계는 뷰포트 가장자리에서 일치한다.

### 5.3 탐색기 컨테이너 높이

`RealEstateMapExplorer.vue:3` 의 `lg:h-[calc(100vh-4rem)]` 를 데스크톱·모바일 양쪽에 적용하고 단위를 `dvh` 로 바꾼다.

```
h-[calc(100dvh-3.5rem)] lg:h-[calc(100dvh-4rem)] lg:min-h-[560px]
```

- **`vh` → `dvh`**: 모바일 브라우저 주소창이 접히고 펼쳐질 때 `vh` 는 갱신되지 않아 스크롤 0이 깨진다. `dvh` 는 실제 표시 영역을 따른다.
- **헤더 높이 두 값**: 헤더는 `h-14 lg:h-16`(56px / 64px, `AppHeader.vue:4`)인데 현재 코드는 `4rem` 하나만 쓴다. 기존엔 `lg:` 에만 적용돼 드러나지 않았지만 모바일까지 확대하는 순간 8px 어긋나므로 브레이크포인트별로 나눈다.
- 지도 영역의 `h-[60vh] lg:h-auto`(`:19`)는 `h-full lg:h-auto` 로 바꾼다. 모바일에서 지도가 컨테이너를 꽉 채우고, 바텀시트는 `fixed` 라 그 위에 겹친다.

### 5.4 사이드바 폭

`lg:w-[22%] lg:min-w-[280px] lg:max-w-[360px]` → **`lg:w-[320px] lg:shrink-0`**.

폭을 1200px 로 묶을 계획이었다면 22% = 264px 라 `min-w` 가 항상 이겨 비율 계산이 죽은 코드가 됐을 것이다. full-bleed 를 유지하기로 했으므로 22% 는 살아 있지만(1512px 화면에서 333px), 화면 폭에 따라 사이드바가 늘었다 줄었다 할 이유가 없다. 목록 항목의 줄바꿈 지점이 화면마다 달라지는 것만 손해다. 고정폭으로 바꾸고 `shrink-0` 를 명시한다.

## 6. 필터바 링크화 — 크롤 경로 보전

### 6.1 문제

하단 유형 카드 7개를 제거하면 링크가 사라진다. 현재 사이트 전체의 부동산 허브 내부 링크는 다음과 같다.

| 대상 | GNB 드롭다운 | 하단 유형 카드 | 그 외 |
|---|---|---|---|
| `apt-sale`, `villa-sale`, `offitel-sale`, `land` | ✅ (`types/facility.ts:550-553`) | ✅ | — |
| **`apt-rent`, `villa-rent`, `offitel-rent`** | ❌ | ✅ | ❌ |

전월세 3개 허브로 가는 내부 링크는 **하단 카드가 유일하다.** 지도 필터바는 `<button>`(`MapFilterBar.vue:5`)이라 크롤 경로가 아니고, 홈의 `HomeTrendingBuildings` 는 건물 상세로만 링크한다. 그냥 지우면 내부 링크 0인 페이지가 3개 생긴다(sitemap `static.xml.ts:98` 에는 남으므로 완전한 고아는 아니다).

**토지는 이 표에서 유일하게 GNB 만으로 버티게 되는 항목이다.** 카드 제거 후 `/real-estate/land` 의 내부 링크는 `types/facility.ts:553` 하나뿐이며, 그 아래 시/도·구군·동 페이지 전체가 이 링크에 매달린다. 토지를 지도 페이지에서 분리하더라도 GNB 링크는 반드시 남긴다(§4).

### 6.2 해법

필터바 버튼을 링크로 바꾼다. 6종 전부가 SSR HTML 에 `<a href>` 로 나타나므로 카드가 하던 역할을 그대로 대신한다. **필터바에 토지를 추가하지 않는다** — 지도 탐색기가 다루지 않는 유형이라 클릭해도 지도가 반응할 수 없다. 토지 링크는 GNB 담당이다.

```vue
<a
  v-for="opt in OPTIONS"
  :key="opt.value"
  :href="`/real-estate/${opt.value}`"
  :aria-current="opt.value === props.type ? 'true' : undefined"
  class="... min-h-[44px] ..."
  @click.exact.prevent="emit('update:type', opt.value)"
>{{ opt.label }}</a>
```

- **`@click.exact.prevent`** — `.exact` 가 없으면 ⌘/Ctrl+클릭 새 탭 열기와 중간 버튼 클릭까지 막힌다. 수식 키가 눌린 클릭은 브라우저 기본 동작(새 탭)으로 흘려보낸다.
- **`aria-pressed` → `aria-current`** — `aria-pressed` 는 토글 버튼용이라 링크에 쓰면 무효다. 현재 선택 상태는 `aria-current` 로 표현한다.
- `min-h-[44px]` 등 크기·색 클래스는 그대로 유지한다. 시각적 변화 없음.
- **`NuxtLink` 가 아니라 `<a>` 다.** 이 링크의 목적은 크롤러에게 href 를 보여주는 것이고 실제 클릭은 항상 `preventDefault` 로 가로채 클라이언트 전환한다. `NuxtLink` 를 쓰면 prefetch 가 붙어 6개 라우트를 불필요하게 미리 받는다.

### 6.3 검증 기준

`/real-estate` SSR HTML 에 `href="/real-estate/apt-rent"`, `villa-rent`, `offitel-rent` 가 각각 최소 1회 나타나야 한다. 이건 회귀 테스트로 고정한다(§9).

## 7. 푸터를 목록 하단으로

### 7.1 배치

`AppFooter` 를 `MapSidebar` 목록 맨 아래에 렌더한다. 사이드바는 이미 `overflow-y-auto` 스크롤 컨테이너(`MapSidebar.vue:2`)라, 목록을 끝까지 내리면 푸터가 나온다. 페이지 스크롤은 0인 채로 푸터 링크 8개와 공공누리 고지가 살아남는다.

`<ul class="flex-1">` 다음에 배치한다. `flex-1` 덕분에 목록이 짧을 때 푸터가 컨테이너 바닥에 붙고, 길 때 목록 뒤로 밀린다.

단, 목록 길이를 제한하지 않으면 이 배치는 제 역할을 못 한다 — §7.5 참조.

### 7.2 `compact` prop

사이드바 폭 320px 에 4열 그리드(`AppFooter.vue:5`)는 들어가지 않는다. `compact?: boolean` 을 추가한다.

| | 기본 | `compact` |
|---|---|---|
| 그리드 | `grid-cols-2 md:grid-cols-4` | `grid-cols-1` |
| 세로 여백 | `py-6 md:py-10` | `py-5` |
| 컨테이너 | `container mx-auto px-4` | `px-4` |
| 내부 폭 제한 | `max-w-4xl mx-auto` | 없음 |
| `mb-8` (그리드 하단) | 유지 | `mb-5` |

**링크·문구·고지문은 하나도 바꾸지 않는다.** 다른 페이지 푸터와 내용이 동일해야 한다.

### 7.3 중복 마운트 차단

`MapSidebar` 는 데스크톱 `aside` 와 모바일 `MapBottomSheet` 두 사본이 **항상 동시에 마운트된다**(안 보이는 쪽은 CSS `hidden`/`lg:hidden` 일 뿐 DOM 에 남는다). 푸터를 그냥 넣으면 링크 8개와 `data-testid="footer-links"` 가 2벌 렌더된다.

`AdBanner` 가 이미 같은 문제를 `isDesktop` 게이트로 막고 있다(`RealEstateMapExplorer.vue:95`). **동일한 게이트를 그대로 쓴다.**

```vue
<!-- 데스크톱 aside -->
<MapSidebar :show-ad="isDesktop === true" :show-footer="isDesktop === true" ... />
<!-- 모바일 바텀시트 -->
<MapSidebar :show-ad="isDesktop === false" :show-footer="isDesktop === false" ... />
```

`isDesktop` 초기값이 `null` 이라 SSR 과 하이드레이션 직후엔 양쪽 모두 `false` 로 평가되어 푸터가 렌더되지 않는다. 이건 `AdBanner` 와 같은 의도된 동작이며 하이드레이션 mismatch 를 막는다. `matchMedia` 결과가 들어오는 순간 정확히 한쪽만 켜진다.

**주의**: `isDesktop === true` 하나만 쓰면 모바일에서 푸터가 영영 사라진다. 반드시 양쪽에 반대 조건으로 넘긴다.

### 7.4 SEO 영향

푸터가 클라이언트 마운트 후에만 렌더되므로 **SSR HTML 에서 푸터 링크 8개가 빠진다.** 이건 감수한다.

- 이 8개(`/about`, `/faq`, `/contact`, `/privacy`, `/terms`, `/search`, `/subscription`, `/real-estate`)는 전 사이트 모든 페이지의 푸터에 있어, 이 페이지 하나가 빠져도 링크 그래프에 실질적 영향이 없다.
- 반대로 §6 에서 보전하는 전월세 3개는 **이 페이지가 유일한 출처**라 SSR 에 반드시 있어야 한다. 그래서 필터바는 `isDesktop` 게이트를 쓰지 않는다.
- 출처 고지(공공누리)가 SSR 에서 빠지는 문제는 없다. `setDatasetSchema` JSON-LD 가 SSR 로 나가며 출처를 명시한다.

### 7.5 목록 페이지네이션 — 푸터 도달성 확보

**문제.** 건물 모드는 최대 200개를 렌더한다(`BUILDING_LIMIT`). 항목 높이 약 62px 기준 목록만 12,400px 이라, 푸터가 목록 뒤에 있으면 아무도 도달하지 못한다. 데스크톱 사이드바(약 979px)에서도 12화면을 내려야 한다. §7.4 에서 푸터가 SSR 에 안 나가기로 한 이상 푸터의 목적은 **사용자 도달** 하나뿐인데, 그 목적을 못 채운다.

**해법.** 건물 모드 목록을 초기 20개만 렌더하고 `[더보기]` 버튼으로 20개씩 늘린다.

| | 목록 전체 렌더 | 초기 20개 |
|---|---|---|
| 데스크톱 · 푸터까지 스크롤 | ~12,100px (12화면) | ~1,020px (1화면) |
| 모바일 펼침 · 푸터까지 스크롤 | ~12,700px | ~1,400px (2.4화면) |

- **무한 스크롤은 쓰지 않는다.** 스크롤이 끝에 닿을 때마다 항목이 추가되므로 푸터에 영원히 도달할 수 없다. 해결하려는 문제를 정확히 악화시킨다.
- **지역 모드(16개)는 페이지네이션하지 않는다.** 이미 한 화면 남짓이고, `SIDO_CHIPS` 16개 링크는 이 페이지의 핵심 SSR 콘텐츠라 전부 HTML 에 있어야 한다.
- 초기 개수 20 은 데스크톱 사이드바 한 화면(약 15개)을 조금 넘긴 값이다. 잘렸다는 사실이 스크롤 없이도 드러난다.
- 광고 삽입 위치(`AD_AFTER_INDEX = 4`)는 초기 20개 안에 있어 영향받지 않는다.
- 더보기는 **클라이언트 슬라이스**다. 서버는 지금처럼 최대 200건을 한 번에 주고, 목록만 잘라 그린다. 추가 API 호출이 없다.
- 뷰포트가 바뀌어 목록이 새로 오면 표시 개수를 20 으로 되돌린다. 안 그러면 이전 지역에서 늘려 둔 개수가 새 지역에 남는다.

**지도 라벨은 200개를 유지한다.** 목록에 맞춰 20개로 줄이면 지도가 휑해져 지도 중심 설계의 의미가 없어진다. 대신 목록 헤더가 차이를 명시한다.

```
이 영역에 1,234곳 — 상위 20곳 표시
```

현재 헤더는 `exact === false` 일 때만 총 개수를 알린다(`MapSidebar.vue:5-7`). 이제 **표시 개수 < 전체일 때** 항상 알리도록 조건을 넓힌다. 목록과 지도의 개수가 다른 이유가 화면에 드러나야 한다 — 라벨이 조용히 사라져 목록 114 vs 지도 76 이 됐던 문제(`726500c4`)와 같은 계열이고, 이번엔 더보기 버튼과 이 문구가 이유를 설명한다.

## 11. 후속 작업

### 11.1 줌 단계에 동(洞) 추가 — 별도 PR

시/도 → 시군구 → **동** → 건물 4단계 요청(2026-08-04). 이번 범위에서 **제외**하기로 결정했다. 레이아웃 전환과 독립적인 기능이고, 함께 넣으면 회귀가 났을 때 레이아웃 탓인지 단계 추가 탓인지 분리되지 않는다. 아래는 오늘 확인한 사실이라 다음 스펙에서 재조사할 필요가 없다.

**가능하다.** 거래 테이블(`AptSaleTransaction` 등)에 `dongName`·`lat`·`lng`·`exclusiveArea` 가 모두 있어, 기존 `buildRegions` 와 같은 형태의 쿼리에 `GROUP BY city, district, dongName` 만 더하면 된다. `Region` 테이블에는 동이 없지만(`@@unique([city, district])`, 267행) 좌표는 거래의 `AVG(lat)`/`AVG(lng)` 로 대신할 수 있어 JOIN 이 필요 없다.

**측정**(로컬 DB, `AptSaleTransaction` 134만 행, 3개월 구간):

| 집계 단위 | 소요 | 결과 행 |
|---|---|---|
| 구·군 | 0.20s | 253 |
| 동 | 0.37s | 2,994 |

스캔 행 수는 같고 GROUP BY 그룹만 늘어나므로 비용 증가가 1.8배에 그친다. 기존 1시간 캐시 뒤라 콜드 1회만 낸다.

**설계상 제약 세 가지:**

1. **응답을 bbox 로 잘라야 한다.** 현재 `fetchRegions` 는 뷰포트와 무관하게 전량을 반환하고 클라이언트가 전부 그린다. 시/도 16개·구군 267개는 괜찮지만 동 약 3,000개를 그리면 지도가 마비된다. 캐시는 지금처럼 `(type, level)` 단위로 전국 1벌을 유지하고 **반환 직전 인메모리 배열 필터**로 자르면 캐시 키가 뷰포트별로 갈라지지 않는다.
2. **동 목록 행은 링크가 아니다.** 아파트·빌라·오피스텔에는 동 페이지가 없다(라우트가 `/real-estate/{type}/{city}/{district}/` 까지). 동 페이지 신설은 3,565 × 6 = 21,390 URL 추가라 thin content 위험이 커서 권하지 않는다. 동 행은 클릭 시 지도를 그 동으로 옮기는 버튼으로 만든다. SSR 은 항상 시/도 모드로 나가므로 크롤 경로에는 영향이 없다. (동 페이지가 있는 건 `land` 뿐이다 — `pages/real-estate/land/[city]/[district]/[dong].vue`)
3. **레벨 경계 재배분**이 필요하다. 히스테리시스 경계도 2개에서 3개로 늘어난다.

| | 현재 | 4단계 |
|---|---|---|
| 시/도 | ≥ 11 | ≥ 11 |
| 시군구 | 8–10 | 9–10 |
| 동 | — | 7–8 |

### 11.2 건물당 매매·전세·월세 병기 — 별도 PR

거래 축(매매/전월세)으로 필터를 나누지 말고, 필터는 **주택유형 3개**(아파트·빌라·오피스텔)로 줄이고 목록의 각 건물 행이 **매매·전세·월세 세 값을 함께** 보여주자는 요청(2026-08-04). 사용자 관점에서 "이 단지, 사면 얼마 / 전세 얼마 / 월세 얼마"가 한눈에 보이는 게 자연스럽다. 방향은 옳지만 **현재 데이터 모델로는 정확히 표현할 수 없다.**

**막는 지점.** `RealEstateBuildingSummary` 는 `@@unique([type, buildingName, bjdCode])` 로 건물+타입당 1행이고, 그 행은 **최신 거래 1건**만 담는다(`latestPrice`, `monthlyRent`, `latestDeal*`). 즉 전월세 행 하나는 전세이거나 월세이지 둘 다일 수 없다.

**운영 데이터 실측**(2026-08-04, 로컬에 복사한 운영 스냅샷, 아파트 기준):

| | 건물 수 |
|---|---|
| `apt-sale` 요약 | 38,045 |
| `apt-rent` 요약 | 40,215 |
| 매매·전월세 둘 다 존재 | 34,313 |
| 전월세 행 중 전세(`monthlyRent = 0`) | 18,802 (47%) |
| 전월세 행 중 월세(`monthlyRent > 0`) | 21,413 (53%) |
| 전월세 행 중 `NULL` | 0 |

따라서 지금 병기하면 **어느 건물이든 최대 두 값만 채워지고**, 어느 칸이 비는지는 "직전 거래가 전세였나 월세였나"라는 우연이 정한다. 월세 물건이 많은 단지가 월세 칸만 비어 보이는 식이라, 데이터 부재로 오독되기 쉽다. 이것이 애초에 거래 축을 2종으로 정한 이유와 같은 제약이다(§4 선행 설계: 3종 분할 시 전세 필터에서 아파트 44.6%·오피스텔 56.4% 누락).

**제대로 하는 방법.** 요약 테이블이 전세와 월세를 **따로** 보관해야 한다. 새 컬럼을 늘리는 것보다 기존 구조를 그대로 쓰면서 `type` 값을 쪼개는 쪽이 자연스럽다 — `apt-rent` → `apt-jeonse` / `apt-wolse`. 그러면 건물당 최대 3행이 되고 `(buildingName, bjdCode)` 로 묶어 세 값을 정확히 병기할 수 있다.

**건드려야 하는 곳과 주의점:**

- `prisma/schema.prisma` — unique 키는 그대로 두고 `type` 값 도메인만 늘어난다(마이그레이션 불필요, 데이터 재생성만).
- **`refreshSummary`** — 전월세를 두 갈래로 나눠 각각의 최신 1건을 뽑아야 한다. ⚠️ 이 함수는 과거 **긴 트랜잭션으로 버퍼풀을 막아 운영 DB 를 세운 이력**이 있다(ledger 상단 MySQL Zombie 항목). 배치 분할과 타임아웃을 반드시 함께 설계한다.
- `realEstateService.getModel()` / `TABLE_NAME_MAP` — 요약의 `type` 과 **거래 테이블 이름은 별개 축**이 된다. 전세·월세 모두 `AptRentTransaction` 에서 나온다.
- **URL 은 바꾸지 않는다.** `/real-estate/apt-rent` 등 6개 슬러그는 정식이며 이 페이지의 유일한 크롤 경로다(§6.1). 요약 `type` 분할은 **내부 표현일 뿐** 라우트·사이트맵·구조화 데이터에 노출되면 안 된다.
- 프론트 `MapFilterBar` 6개 → 3개, `MapSidebar` 행이 세 값을 렌더, `types/realEstate.ts` 매핑.

**§11.1(동 단계)과의 순서.** 둘 다 요약/집계 계층을 건드리므로 함께 설계하는 편이 낫다. 다만 동 단계는 지역 집계(거래 테이블 GROUP BY) 쪽이고 이 항목은 건물 요약 쪽이라, 충돌 범위는 크지 않다.
