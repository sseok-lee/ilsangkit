# 부동산 상세 "주변 버스 정류장" 설계

- 작성일: 2026-10-30
- 상태: 사용자 검토 대기 (결정 반영 완료)
- 출발점: 집품 비교 작업 목록의 보조 항목 "버스 정류장·상가"
  - 이번 범위는 **버스 정류장만**이다. 상가는 별도 작업으로 미룬다.

## 1. 의도

부동산 상세를 보는 사람이 "이 집에서 버스 타기 편한가"를 바로 판단하게 한다.

지금 "주변 생활시설" 섹션은 맨 위에 지하철역을 보여 준다. 대중교통 중 버스가 빠져 있다. 지하철역이 먼 동네일수록 버스 정보가 더 중요하다.

SEO 측면도 있다. 단지마다 주변 정류장 이름과 거리가 다르다. 이 정보가 상세 페이지 사이의 중복 판정을 줄이는 데 도움이 된다(추정).

## 2. 목표 · 비목표 · 반목표

**목표**
- 부동산 상세 "주변 생활시설"에 **버스 정류장** 칸을 추가한다.
  - 반경 **1km** 안의 정류장을 보여 준다.
  - 각 행은 **정류장 이름**과 **직선거리(+도보 약 N분)**다.
  - 가까운 순으로 정렬한다.
- 데이터는 **공공데이터(국토교통부 전국 버스정류장 위치정보)**를 우리 DB에 저장해서 쓴다.

**비목표 (이번에 안 함)**
- 노선 번호, 도착 정보, 배차 간격.
  - 지역별 다른 API를 정류장 수만큼 불러야 한다. 사용자가 "먼저 이름과 거리만"으로 정했다.
- 상가(업종별 개수). 다음 작업이다.
- 시설 상세, 지하철역 페이지 등 다른 페이지의 "주변" 목록.

**반목표 (이러면 실패)**
- **정류장 개별 페이지나 사이트맵 URL을 만드는 것.**
  - 집품 분석 때 "페이지 대량 확장"을 피하기로 했다.
  - 고아 URL과 크롤 예산 문제도 있다.
- **상세 페이지가 외부 API에 의존하는 것.**
  - 페이지를 열 때마다 국토부 API나 카카오 API를 부르는 방식이 여기에 해당한다.
  - 지하철역도 #189에서 같은 이유로 카카오를 걷어냈다.
- 상세 SSR 응답이 눈에 띄게 느려지는 것.
  - 목표: 추가 쿼리 +20ms 이내, 개요 응답 0.5초 이하 유지.

## 3. 사용자가 정한 것

| 항목 | 결정 |
|---|---|
| 표시 내용 | 정류장 이름 + 거리만 |
| 배치 | **A안**: 지하철역 칸(지금은 한 줄 전체)을 반으로 나눠 왼쪽 지하철, 오른쪽 버스. 모바일은 지하철 → 버스 순서로 쌓는다 |
| 반경 | 버스 **1km**. 지하철은 지금처럼 2km |
| 데이터 출처 | 공공데이터(카카오 아님) |
| 구현 방식 | **우리 DB에 저장**(아래 4절 1번 접근) |

시안 파일: `.superpowers/brainstorm/23374-1793316920/content/bus-store-layout.html`의 A안. 반경 표기만 500m에서 1km로 바꾼다.

## 4. 접근 방식 (검토한 것)

| | 방식 | 장단점 | 결론 |
|---|---|---|---|
| 1 | 정류장 파일을 수집해 새 테이블에 저장하고, 상세는 우리 DB에서 1km 안을 읽는다 | 외부 장애가 상세에 영향 없음. 지하철역과 같은 구조. 테이블·마이그레이션·수집 스크립트가 필요 | **채택** |
| 2 | 페이지를 열 때마다 국토부 "좌표 기반 근접 정류소" API 호출 | 저장이 없어 간단함. 대신 봇 포함 모든 조회가 외부 호출이 되고, 한도와 지연이 상세에 그대로 전파됨 | 탈락 |
| 3 | 카카오 로컬 API | 버스 정류장 카테고리가 없어 키워드 검색으로 우회해야 함. 결과 저장 약관과 일일 한도도 확인 필요 | 탈락 |

## 5. 데이터 출처

- **데이터셋:** 국토교통부_전국 버스정류장 위치정보 (data.go.kr 15067528)
  - 현재 최신판 `_20251031`, 206,022행, CSV
  - 이용허락범위 제한 없음, 무료
- **갱신:** 연 1회. 차기 등록 예정일은 2026-10-30이라, 곧 2026년판이 올라올 수 있다.
- **원본 성격:** 지자체 BIS 중 TAGO와 연계된 곳만 들어 있다. 수집일 이후 변동은 반영되지 않는다.
- **실측 (2026-10-30, `_20251031` 파일)**
  - 파일은 **CP949** 인코딩이고 227,065행이다. 포털 표기 206,022행과 다르다.
  - 17개 시·도 전부 들어 있다. 서울 16,980행(서울BIS 12,956 + 경기BIS 4,024), 경기 38,089행 등.
  - `NODE_ID` 중복은 0건이다. 좌표가 한국 범위 밖인 행은 11건이다.
  - 정보수집일은 전 행이 `2025-10-31`로 같다.
  - **같은 정류장이 두 BIS에 중복 등록된 경우가 있다.** 서울에서 같은 이름이 15m 안에 2개인 쌍이 2,743개다. 예: 서울BIS와 경기BIS가 같은 가락시장 정류장을 각각 등록했다.
- **컬럼:** NODE_ID(정류장번호), NODE_NM(정류장명), GPS_LATI, GPS_LONG, COLLECTD_TIME(정보수집일), NODE_MOBILE_ID(ARS 단축번호), CITY_CD, CITY_NAME, ADMIN_NM
- **받는 경로: odcloud API를 기본으로 한다(2026-10-30 사용자 결정).** 최신 판은 Swagger 문서의 판 목록으로 확인한다. 파일 직접 다운로드는 API가 막혔을 때 쓰는 비상 경로(`--local`)다.
- **두 경로 상세:**
  - **odcloud 파일 조회 API:** `https://api.odcloud.kr/api/15067528/v1/uddi:<판별 id>`
    - 활용신청은 2026-10-30에 승인됐다. 키는 `OPENAPI_SERVICE_KEY`로, 청약 동기화와 같은 키다.
    - 승인 직후에는 401 "등록되지 않은 인증키"가 났다. 키가 반영되기 전이라 그런 것으로 보이며, 구현 전에 다시 확인한다.
    - 판(연도)마다 uddi가 다르다. Swagger 문서 `https://infuser.odcloud.kr/oas/docs?namespace=15067528/v1`에 판별 경로가 나열돼 있다.
  - **파일 직접 다운로드:** 로그인 없이 받을 수 있다. 실제로 받아서 확인했다.
    - 1단계: `POST https://www.data.go.kr/tcs/dss/selectFileDataDownload.do`
      - 본문: `publicDataPk=15067528&publicDataDetailPk=uddi:…&fileDetailSn=1&publicDataTyCode=PR0051`
      - 응답 JSON의 `atchFileId`를 쓴다(예: `FILE_000000003558143`).
    - 2단계: `GET https://www.data.go.kr/cmm/cmm/fileDownload.do?atchFileId=…&fileDetailSn=1`
    - 브라우저 UA와 Referer가 필요하다. 이 형식은 data.go.kr WAF 기억에 따른 것이다.

## 6. 설계

### 6.1 저장: 새 모델 `BusStop`

`SubwayStation`처럼 시설 카테고리 레지스트리(`CATEGORY_REGISTRY`)에 넣지 **않는다**. 그래서 목록 페이지, 상세 페이지, 사이트맵, 검색에 섞이지 않는다.

필드는 원본 컬럼을 전부 저장한다(데이터 수집 최대화 원칙).
- `nodeId`(PK 또는 unique, NODE_ID), `name`, `lat`·`lng`(Decimal(10,7))
- `mobileId`, `cityCode`, `cityName`, `adminName`, `collectedAt`(원본 문자열)
- `sourceVersion`(판 식별자, 예 `20251031`), `syncedAt`
- 인덱스: `lat`, `lng`. `SubwayStation`과 같은 사각형 검색용이다.

좌표가 없거나 한국 범위(`KOREA_BOUNDS`) 밖인 행은 버리고 개수를 기록한다.

### 6.2 수집

- `backend/src/scripts/syncBusStop.ts` + 서비스 1개. `baseSyncService`의 `runSync`·`batchUpsert`(500건) 패턴을 쓴다.
- **판 단위 교체:** 새 판을 다 넣은 뒤, 그 판에 없는 정류장(`sourceVersion`이 다른 행)을 지운다.
  - 넣다가 실패하면 지우지 않는다. 옛 데이터가 남아도 화면은 계속 나온다.
- **이미 같은 판이면 건너뛴다.** 매달 돌려도 실제 적재는 1년에 한 번이다.
- **안전장치:** 새 판 행 수가 직전 판의 80% 미만이면 저장하지 않고 실패 처리한다. 원본이 깨졌을 때 정류장이 대량으로 사라지는 걸 막는다.
- **중복 정류장:** 원본 행은 모두 저장한다. 합치기는 API 단계에서 이름 기준으로 한다(6.3).
- 단독 스크립트 `syncBusStop.ts`로 실행할 수 있고, `syncAll.ts`에도 `bus-stop` 카테고리로 추가한다(사용자 확인).
- **실행 방식:** 시설 수집처럼 **사용자가 직접 실행**한다(2026-10-30 사용자 결정). cron은 등록하지 않는다.
  - 낮 시간은 피한다. 첫 적재는 지금 있는 `_20251031`판으로 하고, 2026년판이 올라오면 다시 돌린다.

### 6.3 API

- 기존 `GET /api/transit/nearby` 응답에 `busStops`를 **추가**한다. 기존 `stations`는 그대로 둔다.
  - `busRadius` 쿼리는 기본 1000, 최대 2000.
  - `busStops: [{ id, name, distance }]`, 거리순, 최대 5곳.
  - `busStopCount`는 반경 안 **전체 개수**다. 상한을 두지 않는다.
  - **같은 이름은 한 줄로 합친다**(2026-10-30 사용자 결정).
    - 두 BIS의 중복 등록과 길 건너편 양방향 정류장이 모두 여기에 해당한다.
    - 합친 행의 거리는 가장 가까운 정류장의 거리다.
    - `busStopCount`도 합친 이름 기준으로 센다.
- 검색 방식은 `findNearbyStations`와 같다. 위경도 사각형으로 후보를 고르고 haversine으로 거르고 정렬한다.
  - 도심 1km 사각형은 후보가 100~200곳 수준이라 앱 메모리로 충분하다(추정).
- 호출 하나로 지하철과 버스를 같이 받으니, 화면의 추가 요청은 0이다.

### 6.4 화면 (`frontend/components/realEstate/NearbyFacilities.vue`)

- 지하철 칸의 `md:col-span-2`를 없애고, 지하철과 버스 두 칸을 나란히 둔다.
  - 버스 정류장이 0곳이면 지금처럼 지하철이 한 줄 전체를 쓴다.
  - 지하철역이 0곳인데 버스는 있으면 버스가 한 줄 전체를 쓴다.
- **버스 칸**
  - 제목: "버스 정류장"
  - 오른쪽 개수: "반경 1km · N곳". N은 `busStopCount`, 즉 이름 기준 전체 개수다. "이상" 표기는 쓰지 않는다
  - 행: 이름 + 거리 + 도보 약 N분. 지하철 행과 같고 배지는 없다.
  - 최대 5곳, 모바일은 3곳 뒤에 "모두 보기"
- **링크:** 정류장 페이지가 없으므로 행이 **링크가 아니다**.
  - 지금 `NearbyPlaceRow`는 항상 링크(`to` 필수)다. 링크 없는 행을 그릴 수 있게 해야 한다.
  - 크롤러가 따라갈 가짜 링크(`#` 등)를 만들지 않는다.
- **하단 출처 문구**에 "버스정류장: 국토교통부 · YYYY년 MM월 수집"을 덧붙인다.
  - 날짜는 원본 `정보수집일`(`collectedAt`)이다. 현재 판은 전 행이 2025-10-31이다. 신뢰 디자인 원칙상 출처를 분명히 한다.
- SSR로 그린다. 지금 `useAsyncData` 경로를 그대로 쓴다.

## 7. 제약

- **Node 20**, ESM `.js` import, 라우트는 `asyncHandler`, 에러는 에러 클래스를 쓴다(CLAUDE.md).
- **마이그레이션 순서:** 운영 DB에 마이그레이션을 먼저 적용한 뒤 코드를 배포한다. 배포는 스키마를 바꾸지 않는다.
- **운영 서버:** OCI 2코어, 여유 메모리 약 2~3GB.
  - 수집은 스트리밍 또는 페이지 단위로 한다. 20만 행을 한 번에 메모리에 올리지 않는다.
  - 사용자 많은 낮 시간에는 돌리지 않는다.
- **PR 기반:** develop을 거쳐 main으로 간다. TDD, 커밋 전 vitest.
- 브라우저 API 접근에는 SSR 가드를 둔다.
