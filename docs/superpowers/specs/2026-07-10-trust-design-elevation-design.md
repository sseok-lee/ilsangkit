# 신뢰 디자인 격상 (Trust Design Elevation) — 디자인 스펙

- 날짜: 2026-07-10
- 상태: 사용자 디자인 승인 완료 (B안 + 목업 확인), 스펙 리뷰 대기
- 목업: 같은 폴더의 `2026-07-10-trust-design-mockup.html` (데스크톱 컴포넌트 8종), `2026-07-10-trust-design-mockup-mobile.html` (모바일 상세 섹션 사다리 A/B + 홈 히어로 C), `2026-07-10-trust-design-mockup-gnb.html` (GNB 아이콘 정리 3안 비교 — C안 채택)

## 1. 배경과 문제의식

사용자 진단: "사이트 전체 인상이 가벼워 개인 사이트처럼 보이고, 모든 페이지의 완성도가 아쉬워 신뢰감이 부족하다."

5개 렌즈 리서치(경쟁사 ayo.pe.kr·local.114 실측 / 부동산 플랫폼 6곳 / 공공데이터 서비스 7곳 / 학술·실무 신뢰 연구 / 일상킷 라이브 SSR 감사)가 하나의 결론으로 수렴했다:

> **일상킷의 신뢰 부족은 색·폰트 문제가 아니라 "증빙 밀도" 문제다.**
> 코발트 `#2450DC` + 그레이 + Pretendard 토큰은 경쟁·레퍼런스와 동일 계열로 이미 옳다.
> 부족한 것은 (a) 데이터 인접 위치의 출처·기준일 표기, (b) 운영 실체 표시,
> (c) 디테일 결함 제거, (d) 첫 뷰포트의 무게감, (e) 광고와 콘텐츠의 시각 계약이다.

핵심 근거:
- Fogg(Stanford, 2,684명): 신뢰 판단 코멘트의 46.1%가 시각 인상(design look). 판단은 ~50ms에 형성.
- 호갱노노 "국토교통부에서 28분 전 확인"+원본 링크, 부동산지인 "출처·수집일·기준일" 3단 라벨, KB "07.09 기준" — 전문 플랫폼의 신뢰는 "모든 숫자에 붙은 메타데이터"에서 나온다.
- ayo: 최상단 공공데이터 배너 → 상세 DATA SOURCE/UPDATED 카드 → 푸터 사업자 정보까지 "어느 스크롤 위치에서도 증빙이 보이는" 구조.
- 일상킷 라이브 감사: 출처·동기화 장치는 이미 존재하나 **전부 페이지 최하단**. 데이터를 판단하는 지점(시세 통계·운영시간·집계 수치)에는 기준일 노출 0회. 지역 허브 집계 수치는 기간 표기 전무.
- Stanford #2/#4/#5(운영 주체 표시)·한국 831명 실증(규범 요소 표시 최상위 요인) ↔ 일상킷 푸터에 연락처 없음, About "소규모 개발팀" 익명, 콘텐츠 56건 무기명.
- Baymard: 레이아웃 버그·디테일 결함은 "해킹당한 사이트" 의심까지 유발 — 신뢰를 불균형하게 깎는다.

일상킷이 경쟁사보다 이미 나은 것(유지·부각 대상): SSR 렌더링, 개인정보처리방침·이용약관(경쟁 2사 모두 없음), About 21행 출처 테이블, Contact 응답 SLA, 매수/매도 주체까지 있는 고밀도 거래 표.

## 2. 목표 / 비목표

**목표**
1. 도착 후 0.5초의 무게감: 첫 뷰포트에서 "공공데이터 기반의 관리되는 서비스"로 읽히게 한다.
2. 어느 스크롤 위치에서도 보이는 증빙: 데이터 블록마다 출처·기준일이 인접 노출된다.
3. 운영 실체의 가시화: 팀명·연락처·정정 채널이 전 페이지에서 보인다.
4. 신뢰를 깎는 디테일 결함 8종 제거 + 재발 방지 테스트.

**비목표 (이번 범위에서 하지 않는 것)**
- 페이지 구조·섹션 순서·URL 재편 (C안 기각 — 이전 전면 재설계 revert 이력 + SEO 회복 국면 리스크)
- 파생 지표(전세가율)·지역 벤치마크 비교·프로즈 시황 요약·실시간 상태 칩 (§11 Phase 3 후보로만 기록)
- 광고 슬롯 개수·위치 변경 (수익 정책은 사용자 결정 영역)
- 다크 모드, 리브랜딩(색 체계 교체)

## 3. 불변식 (구현 전 과정에서 지킬 것)

- **SEO/SSR**: URL 구조, 단일 h1, title/meta 생성 로직(동결된 title 정책 포함), canonical, noindex 게이트, 사이트맵·lastmod 로직 — 전부 불변. SSR 텍스트는 늘어나는 방향만 허용.

- **디자인 토큰**: 라이트 전용, 코발트 `#2450DC`, OD 중성 잉크 스케일, 카테고리 16색, Pretendard/Public Sans, 2단계 radius — 유지. 신설 토큰은 §7-4 등락색 2종뿐.

## 5. Phase 1 — 신뢰 장치 계층 (저위험 선행)

### 5-1. `SourceStamp` 컴포넌트 (핵심 신설)

데이터 블록에 인접 배치하는 출처·기준일 캡션의 단일 규격.

- **문법**: `출처 {기관명} · 기준 {YYYY.MM} · {YYYY.MM.DD} 동기화 · [원본 보기 ↗]`
  - "기준"(데이터 자체의 기준 시점, 예: dealYmd 최신월)과 "동기화"(수집 시점, SyncHistory 최근 성공)를 구분 표기. 해당 없는 항목은 생략.
- **variant 2종**:
  - `capsule` — 테두리 있는 알약형 + 상태점(초록 = 최근 동기화 성공). 데스크톱 섹션 헤더용.
  - `plain` — 테두리 없는 텍스트형. 각주 위치·모바일 공용. **모바일은 항상 plain**.
- **props**: `provider`(기관명, 필수) / `basisDate`(기준, 옵션) / `syncedAt`(동기화, 옵션) / `sourceUrl`(원본 딥링크, 옵션 — `CATEGORY_DATA_PORTAL_URL` 및 국토부 rt.molit.go.kr 재사용) / `variant`.
- **stale 가드 (필수)**: `syncedAt` 경과가 해당 데이터 갱신 주기의 2배를 넘으면 날짜·상태점을 숨기고 출처·링크만 렌더. 갱신 주기 기준: 부동산·청약(daily sync) = 2일, 시설(월 1회) = 62일. 근거: 부동산지인 홈에 "기준일: 2022-02-11"이 4년째 잔존하는 반면교사 — 낡은 날짜는 무표기보다 나쁘다.
- **적용 위치 (필수)**:
  1. 부동산 상세: 매매/전세가 추이 차트 헤더, 거래 내역 표 헤더(+원본 보기 링크)
  2. 시설 상세: 기본정보 섹션 헤더
  3. 목록 스탯 스트립: "월 1회 자동" 선언 옆에 실제 동기화 날짜 병기 (§7-3 카운터 밴드로 통합)
  4. 지역 허브: 시세·시설 집계 블록
  5. 홈 "오늘의 부동산 시장": 기존 각주를 SourceStamp 규격으로 통일
- SSR 텍스트로 렌더(크롤러 가시). 날짜·건수가 페이지별 실데이터이므로 형제 페이지 중복(boilerplate) 유사도에는 오히려 차별화 방향.

### 5-2. 집계 수치 산출조건 병기 규칙

"숫자가 단독으로 서지 않는다": 집계 수치를 보여주는 스탯 컴포넌트에 산출조건 라벨 슬롯을 추가하고, 집계형 수치에는 채움을 필수화한다.

- 형식: 수치 아래 11~12px faint 텍스트. 예: `최근 1년 · 국토교통부 신고 기준`, `최근 3개월 실거래 1,204건 중앙값`, `최근 7일 vs 직전 7일 · 표본 30건 미만 제외`.
- 최우선 적용: 지역 허브의 "평균 매매가·거래 건수"(현재 기간 표기 전무 — 누적치 여부 판별 불가). 규칙: **이번 범위에서는 현행 쿼리의 실제 산출 조건을 정직하게 표기**한다(누적치면 "전체 기간 누적"으로). 기간 스코핑 변경(예: 최근 1년로 축소)은 쿼리·수치 영향이 있으므로 구현 계획 단계에서 별도 결정 항목으로 다룬다. 어떤 경우든 표기와 실제 쿼리의 불일치는 금물.
- 원시 단건 수치(개별 거래가·주소·전화번호)는 대상 아님.

### 5-3. 푸터 운영 실체 블록 + 전 페이지 트러스트 라인

- **트러스트 라인**: 홈 전용 "공공데이터 기반 서비스" 박스의 1줄 축약판을 전 페이지 푸터 직전 공통 슬롯으로. `✓ 공공데이터 기반 서비스 — 행정안전부·국토교통부·보건복지부 등 공식 API/CSV를 공공누리(KOGL) 조건에 따라 사용합니다 [전체 출처 보기 → /about#data-sources]`. 홈은 기존 확장판 박스 유지(중복 아님 — 홈만 확장판으로 대체).
- **푸터 운영 블록** (팀명+이메일 수준):
  - `운영 일상킷 팀 · 문의 contact@ilsangkit.co.kr`
  - `정보 수정 요청 → (Contact 데이터 오류 유형 딥링크) — 확인 후 3~5일 내 반영` (기존 Contact SLA의 승격)
  - `데이터 최종 동기화 {YYYY.MM.DD HH:mm}` (SyncHistory 전체 최근 성공, stale 가드 동일 적용)
  - 면책 1줄: `본 서비스의 정보는 공공데이터포털(data.go.kr)·국토교통부 실거래가 공개시스템 자료를 가공한 참고용 정보입니다.`
- 기존 푸터 구성(서비스/정보·지원/법적 고지, KOGL 문구)은 유지하고 위 블록을 브랜드 컬럼에 추가.

### 5-4. 상세 "데이터 출처" 카드 강화

기존 최하단 출처 카드에 2개 추가:
- `정보가 실제와 다른가요? 수정 요청 →` 링크 (Contact 데이터 오류 유형으로, SLA 문구 동반)
- 데이터셋 행을 About 출처 테이블의 해당 행 앵커(`/about#data-sources` + 행 id) 또는 data.go.kr 원본으로 딥링크

### 5-5. 콘텐츠 바이라인

가이드·기사(현재 56건, 전부 무기명)의 카드와 상세에 바이라인 추가:
- `일상킷 데이터팀 · {YYYY.MM.DD} 발행 · ✓ 공공데이터 원문 대조 검수`
- "검수" 문구는 어드민 검토·발행 플로우를 실제로 거치는 콘텐츠(guide, article 모두 해당)에만. 저자명 상수는 `일상킷 데이터팀` 단일.
- 상세 페이지 구조화 데이터(author)에도 동일 값 반영 (Organization/팀 명의).

### 5-7. 광고 시각 계약

- 슬롯 위 10px "광고" 마이크로 라벨(uppercase, faint)
- 본문과 구분되는 컨테이너: 점선 테두리 + surface-2 배경
- 슬롯 수·위치·고정 높이·collapse 정책 불변 (§3)
- 근거: NN/g 452명 — 신뢰 손상은 광고량이 아니라 "콘텐츠 위장·재배치"에서. Stanford #9 — 스폰서 콘텐츠 명확 구분.

1. **어미**: 사용자 대면 문장은 해요체로 통일 (표 셀·라벨 제외)
2. **금액**: 억/만 축약 표기 단일 유틸 (`6억 9,800만`), 원 단위 병기 금지
3. **날짜**: 본문 `YYYY.MM.DD`, 표 안 `YY.MM.DD`, 메타 정보 `YYYY-MM-DD` 허용
4. **빈 값**: `정보 없음 · 현장 확인 필요` 패턴 (숨기지 않고 정직하게, 단 연속 빈 필드는 섹션 접기 — 기존 degrade 규칙 유지)
5. **생성문체 정리**: "~를 안내합니다 / ~를 살펴봅니다" 반복 종결 등 상투 표현을 요약문에서 제거(기존 콘텐츠는 배치 수정, 생성기 프롬프트도 동일 규칙 반영)
6. 근거: 토스 UX 라이팅 — "일관적이고 비문 없는 문장"이 Reliable 브랜드 감정의 구현체

## 6. Phase 2 — 첫인상 무게감

### 6-1. 헤더 + GNB 아이콘 정리

- 로고 옆 마이크로 라벨 1줄: `공공데이터 기반 생활정보` (데스크톱만, 모바일 생략 — 히어로 스탬프가 역할 대체). 좌측 보더 구분, 11px, faint.
- **GNB 아이콘 전면 제거 (사용자 결정: C안, GNB 비교 목업 참조)**:
  - 탑레벨 트리거(부동산·청약임대·공매·생활시설)와 유틸 링크(가이드·소개)의 장식 아이콘 제거 — 텍스트-온리. `expand_more` 캐럿은 기능 어포던스이므로 유지.
  - 메가메뉴 패널 내부의 카테고리 webp 아이콘·그룹 아이콘도 제거 — 텍스트 리스트로.
  - 모바일 햄버거 메뉴도 동일하게 텍스트-온리 (일관성, `2026-07-10-trust-design-mockup-gnb-mobile.html` 비교 목업 참조). 행 높이(≥42px 터치 타깃)·들여쓰기·hover 틴트 피드백은 유지하고 아이콘 요소만 제거. 그룹 간 상단 여백을 한 단계 확대해 3단 타이포 위계(그룹 eyebrow → 서브그룹 → 항목)가 스캔을 담당.
  - **스캔성 보완 규칙**: 패널 그룹 헤더를 eyebrow 위계(11px·uppercase·faint)로 유지·강화, 항목 행 높이·hover 배경 유지, 컬럼 간격 충분히. 15개 항목이 텍스트 벽으로 읽히지 않게 그룹 리듬으로 보완.
  - **적용 범위 한정**: GNB·모바일 메뉴에만 해당. 홈 카테고리 그리드, 시설 카드, 섹션 헤더 등 GNB 외 카테고리 아이콘 사용처는 유지.
- **구현 주의**:
  - GNB는 SSR 노출용 `v-show` 구조 — 링크 렌더링·개수는 불변, 아이콘 요소만 제거 (사이트링크 요인 보호).
  - 안 쓰게 된 material symbol을 `nuxt.config` `icon_names`에서 뺄 때: 타 사용처 grep 확인 → 알파벳 정렬 유지 → `.nuxt`/`.output` 삭제 후 dev 재시작.
- 헤더 구조·링크 구성 자체는 변경 없음.

### 6-2. 홈 히어로 — "날짜가 박힌" 코발트 데이터 패널

- 현재 흐릿한 건물 사진 배경 제거 → **단색 딥 코발트 패널**(`--brand-press #16358F`, 그라데이션 금지)
- 구성: 출처 배지 2개(공공데이터포털·국토교통부 실거래가) + 우측 기준일 스탬프(`{YYYY.MM.DD} 기준 · 매일 자동 동기화`, 실거래 SyncHistory 최근 성공일, stale 가드 적용) → H1(기존 카피 유지) → 검색창 → 스탯 4칸
- 스탯 4칸: 기존 3종(실거래 부동산·진행중 청약·등록 시설) + **오늘 업데이트 N건**(기존 "오늘 신규 등록" 배지 데이터 재사용)
- 모바일: 배지 1개로 축약 + 스탬프 유지, 스탯 2×2
- 단일 h1 유지, SSR 텍스트 유지. nitro route cache 퍼지 후 검증(기존 메모리 교훈).

### 6-3. 목록·허브 카운터 밴드

기존 목록 스탯 스트립을 4칸 밴드로 개편: `이 지역 N곳 | 전국 등록 N곳 | 최근 동기화 {날짜} | 갱신 주기 {월 1회 자동}`
- 전국 카테고리 목록·지역×카테고리 목록·부동산 목록·지역 허브에 공통 적용
- "선언(월 1회 자동) → 증명(실제 날짜)" 완결이 목적. 수치는 전부 기존 DB·meta API 보유분.
- 모바일 2×2 (od-hero-stats 규칙 재사용)

### 6-4. 숫자 타이포 규칙 전역화

- `font-variant-numeric: tabular-nums`를 숫자 표·스탯 전역 적용 (현재 일부만)
- 표의 숫자 컬럼 우측 정렬 통일
- 등락 표기 토큰 신설: `--delta-up: #DC2626`(상승·빨강), `--delta-down: #2563EB`(하락·파랑) — 한국 금융 관례. 기존 화면의 등락 표기(홈 시장, 부동산 상세, 허브)를 이 토큰으로 통일. semantic error/success와 분리(혼용 금지).
- 금액 축약·날짜 포맷은 §5-8 유틸 공유

### 6-5. 상세 스펙 스트립

상세 헤더(H1·주소 아래)에 파이프 구분 핵심 팩트 1줄. 페이지 구조 변경 없음 — 헤더 블록에 1줄 추가.
- 부동산: `전용 {범위}㎡ | {준공연도}년 준공 ({N}년차) | 총 {N}세대` (연차 자동 계산)
- 시설: 카테고리 레지스트리에 스트립 필드 최대 3개 정의 (예 — 약국: 오늘 영업시간·약사 수 / 주차장: 요금·면수·노외 구분). 카테고리별 매핑은 구현 계획에서 확정.
- **degrade 규칙**: 값 없는 항목은 생략, 전부 없으면 스트립 미렌더 (빈 파이프 금지)
- 모바일: 줄바꿈 허용, 항목 3개 이하
- 유래: revert된 상세 재설계의 스펙그리드 자산 중 저위험 요소만 선별 재도입

### 6-6. 로고 코발트 재작업

- 핀 심볼·워드마크를 `#2450DC` 계열로 재채색 (원본이 래스터뿐이면 SVG로 재작성 후 채색)
- 교체 대상 일괄: 헤더/푸터 로고, favicon, OG 기본 이미지, PWA 아이콘 등 로고 사용처 전수
- 주의: OG 이미지 교체 시 네이버 PNG 요건 유지 (webp/SVG og:image 금지 — 기존 메모리 원칙)

## 7. 모바일 규칙 (전 항목 공통)

1. SourceStamp는 항상 `plain` variant — 섹션 제목 우측, 좁으면 아래 줄로 개행
2. 헤더 마이크로 라벨 생략 — 히어로 기준일 스탬프가 대체
3. 스탯·카운터 밴드는 2×2 그리드
4. 스펙 스트립 줄바꿈 허용·3항목 이하
5. 표는 기존 가로 스크롤 컨테이너 유지(컬럼 축소 금지 — 고밀도가 강점) + 스크롤 힌트 텍스트
6. 섹션 순서·개수는 기존 모바일 사다리 그대로 (구조 변경 0)

## 8. 데이터 요구사항 (백엔드 접점)

- SyncHistory 최근 성공 시각의 카테고리별 노출: 시설 상세·목록은 기존 응답에 이미 존재(약국 상세 "최근 동기화 2026-06-19" 실측). 부족한 표면(지역 허브, 홈 스탬프, 푸터 전체 최종 동기화)은 기존 meta API 확장으로 제공 — 신규 테이블 없음.
- 총계 카운트(전국 N곳)는 기존 목록 스탯 스트립 데이터 재사용.
- 지역 허브 집계의 산출 기간 정의(§5-2)는 백엔드 쿼리와 표기 문구를 한 곳(상수)에서 공유.
