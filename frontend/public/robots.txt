# 네이버 검색로봇
# 페이지네이션(/*?page=)은 차단하지 않는다 — 2026-05 에 "크롤 예산 절약"으로 넣었다가 되돌린 규칙이다.
# 목록 2페이지 이후는 HTML 에서 이미 noindex, follow 로 나간다. 즉 색인 비대는 noindex 가 막고 있고,
# 그 페이지에 남는 유일한 가치는 "상세로 가는 링크 통로"뿐이다. robots 로 크롤을 막으면
# 그 통로만 끊기고 얻는 것이 없다(크롤러는 가져오지 못한 페이지의 링크를 따라갈 수 없다).
# 같은 실수를 wifi 상세에서 이미 했다 — 2026-07-09 에 차단했다가 색인이 동결돼 07-28 에 해제했다.
# 크롤 예산이 걱정되면 sitemap 제외와 noindex 로 다루고, robots 차단은 쓰지 않는다.
User-agent: Yeti
Allow: /
Allow: /_nuxt/
Allow: /api/images/
Disallow: /api/
# Nuxt _payload.json 은 SSR HTML 의 중복 데이터 — 크롤 예산 낭비 차단 (?buildId 쿼리 때문에 $ 앵커 미사용)
Disallow: /*_payload.json
Disallow: /admin

User-agent: *
Allow: /
Allow: /_nuxt/
Allow: /api/images/
Disallow: /api/
# Nuxt _payload.json 은 SSR HTML 의 중복 데이터(종종 HTML 보다 큼). 크롤만 차단해 크롤 예산을
# 본문 HTML 색인에 집중시킨다. 브라우저 클라이언트 네비게이션은 robots 영향을 받지 않는다.
# payload URL 에 ?<buildId> 쿼리가 붙으므로 $ 앵커는 쓰지 않는다(붙이면 매칭 실패).
Disallow: /*_payload.json
Disallow: /admin
# og-map 은 상세 og:image 가 가리키는 소셜 미리보기 생성 라우트다. 상세마다 쿼리스트링이 달라
# URL 이 전부 고유하므로 크롤러가 개별 리소스로 끝없이 수집한다.
# 실측(2026-08-26): Googlebot 요청 619건 중 og-map 이 163건(26.3%)으로 1위였고, 응답이
# 837KB/0.411초라(상세 HTML 은 71KB/0.058초) 바이트로는 og-map 136MB 대 콘텐츠 20MB —
# 크롤 대역폭의 약 87% 였다. 같은 날 Googlebot 은 318건뿐인데 bingbot 7,717·Yeti 8,777 이었고
# 콘텐츠 전량 크롤에 약 4.9년이 걸리는 속도였다.
# 여기서는 wifi·페이지네이션과 달리 robots 차단이 옳은 도구다 — 바이너리 이미지라 meta robots 가
# 없어 "크롤해야 noindex 를 확인한다"는 회수 경로 문제가 없고, 검색 결과에 나오지 않아 잃을 색인 자산도 없다.
# 단 Yeti 와 소셜 스크레이퍼에는 넣지 않는다(아래 각 그룹 참고).
Disallow: /og-map

# wifi 상세(/wifi/wifi-) 는 크롤 차단하지 않는다 — 검색엔진 그룹(Yeti·*)에 Disallow 를 두지 말 것.
# 이유: wifi 상세는 pages/[category]/[id].vue 에서 영구 noindex 로 나가는데, noindex 는 크롤러가
# 페이지를 실제로 가져와야만 확인된다. robots.txt 로 막으면 크롤러는 "이미 수집해 둔 사본"을
# 재평가할 방법이 없어져 색인/진단에 영구 고착된다(= 색인 제거가 아니라 색인 동결).
# 2026-07 에 이 Disallow 를 넣었다가 정확히 그 현상이 관측됐다: 네이버 중복 title 진단의 wifi 657건이
# 마지막 크롤 06-29 에 멈춘 채 7월 크롤 0건이었고, SEO 이슈 문서 수가 한 번도 감소하지 못했다.
# 크롤 예산이 걱정되면 sitemap 제외(sitemapPolicy.ts)와 noindex 로 다루고, robots 차단은 쓰지 않는다.
# AI 크롤러 그룹은 색인 회수와 무관하고 순수 부하만 유발하므로 아래에서 계속 차단한다.

# AI 검색 크롤러 — 본문은 허용하되(AI 검색 노출) 크롤 예산 낭비 경로는 User-agent: * 와 동일하게 차단한다.
# robots.txt 그룹은 상속되지 않는다 — 자기 이름 그룹이 있는 봇은 User-agent: * 를 통째로 무시하므로

# 41,741 회(52%)를 _payload.json(28,814)·/wifi/wifi-(12,927)에 쏟아 서버 부하만 유발하고 있었다.

# Amazon 크롤러 계열 — 같은 이유로 차단 (2026-08-26).
# Amazon 공식 문서(developer.amazon.com/support/amazonbot)에 수집 데이터가
# "may be used to train Amazon AI models" 라고 명시돼 있고 나머지 용도는 Alexa 검색 지원이다.
# 위 GPTBot·PerplexityBot 을 허용한 근거는 "AI 답변이 출처를 인용해 유입이 생긴다"인데,
# Alexa 는 한국 사용자에게 웹 출처를 보여주지 않는다 — 인용 표면이 없으므로 그 근거가 성립하지 않는다.
#
# 실측(2026-08-26, 2일): Amazonbot 30,079 요청으로 이 사이트 최대 크롤러였다
# (Yeti 8,777/일·bingbot 7,717/일을 상회). 경로는 real-estate 6,712 · og-map 6,119 ·
# wifi 2,974 · hospital 2,805 · childcare 2,039. crawl-delay 를 지원하지 않아 감속 수단도 없다.
# 역방향 DNS 로 진위 확인됨(상위 40 IP 중 39개가 *.crawl.amazonbot.amazon).
#
# IVT 와는 무관하다 — _nuxt 번들 요청이 30,079건 중 2건뿐인 순수 HTML 페처라 애드센스 스크립트를
# 로드하지 않고 광고 노출을 만들지 않는다(대조: Googlebot 은 619건 중 142건). 차단 근거는 순수 부하다.
